# Plan: Shared Team Memory Profile for Claude Code

## TL;DR
Build `sharing-is-caring` — a Python CLI + JSON/YAML schema that lets a team
maintain a **shared memory profile** in a git repo, layered with per-user
overrides, and compiled into the `CLAUDE.md` files Claude Code natively reads.
Conflicts are resolved in three tiers: (1) personal override wins, (2) team
default wins, (3) LLM-mediated merge as a fallback for genuinely contradictory
preferences. Inspired by the MatMaq Medium article (Mar 2026); no existing OSS
tool covers this end-to-end (closest: roampal, mempalace, spec-kit-memory-hub —
all individual or non-Claude-Code-native).

## Recommended Integration: CLAUDE.md generation
Claude Code already supports a layered memory system natively:
- `~/.claude/CLAUDE.md` — user-level (loaded for every session)
- `<repo>/CLAUDE.md` — project-level (loaded when in repo)
- `@path/to/file.md` — import syntax inside CLAUDE.md
- `.claude/settings.json` — project settings

So v1 doesn't need an MCP server. The CLI compiles `team.yaml + personal.yaml`
into a deterministic `CLAUDE.md` with `@imports` for modular sections. MCP
server is a Phase 2 add-on if live querying is needed.

## Phases & Steps

### Phase 1 — Schema & core model (foundation, blocks everything)
1. Define **profile schema** (JSON Schema + Pydantic models) with sections:
   `identity`, `languages`, `tools`, `coding_style`, `workflow`, `domain_knowledge`,
   `do_not`, `free_form`. Each entry tagged with `scope` (team|personal),
   `priority` (0–100), `owner`, `updated_at`, `rationale`.
2. Define **layer model**: `base (team) → personal override → resolved`.
   Resolution rules per field type (scalar, list-append, list-replace, map-merge)
   declared in schema.
3. Write fixtures: `examples/team.yaml`, `examples/alice.personal.yaml`,
   `examples/bob.personal.yaml` (one with deliberate conflicts).

### Phase 2 — CLI scaffold (depends on Phase 1)
4. Pick stack: Python 3.11 + `typer` (CLI) + `pydantic` v2 + `ruamel.yaml`
   (preserves comments/order) + `rich` (pretty diffs) + `pytest`. Anthropic
   SDK only pulled in for the LLM-merge command.
5. Project layout: `src/sic/{schema,loader,merger,renderer,cli,llm}.py`,
   `tests/`, `examples/`, `pyproject.toml`. Package name `sharing-is-caring`,
   command `sic`.
6. Implement commands as stubs first, fleshed out in later steps:
   `sic init`, `sic validate`, `sic merge`, `sic render`, `sic sync`,
   `sic diff`, `sic conflicts`, `sic import-chatgpt`.

### Phase 3 — Merge engine + tiered conflict resolution (depends on Phase 1)
7. **Tier 1 — Personal override**: any field with `scope: personal` and
   matching key replaces team value. Pure deterministic merge.
8. **Tier 2 — Team-wins default**: when only team value exists, it's used.
   Personal additive lists are appended unless team marks the field
   `lock: true`.
9. **Tier 3 — LLM-mediated**: when two same-priority team entries (or two
   personal entries from different imports) genuinely contradict, call
   Claude via Anthropic SDK with a structured prompt: returns either a
   merged value or `{"action": "ask_human", "reason": "..."}`.
   Cache results in `.sic/merge-cache.json` keyed by content hash so the
   same conflict doesn't re-bill.
10. `sic conflicts` command lists unresolved items with three options:
    accept-team / accept-personal / open-llm-merge.

### Phase 4 — Renderer (CLAUDE.md output) — *parallel with Phase 3*
11. `sic render --target user` writes `~/.claude/CLAUDE.md`;
    `sic render --target project` writes `<repo>/CLAUDE.md`.
12. Output is a stable, sectioned Markdown file with a header banner
    (`<!-- generated by sic vX.Y from team@<sha> + personal@<sha> -->`)
    and `@imports` to split large sections (e.g., domain glossary) into
    files under `.claude/sic/`.
13. Idempotency: re-running with no input changes produces byte-identical
    output. Verified by golden-file tests.

### Phase 5 — Git workflow (depends on Phase 2)
14. `sic init --team-repo <url>` clones the team profile repo into
    `~/.sic/team/`, sets up a remote, and creates a stub
    `~/.sic/personal.yaml`.
15. `sic sync` = `git pull` on the team repo + re-run merge + re-render.
    Designed to be wired into a shell hook or run before each Claude Code
    session.
16. Document the team-side workflow: PRs against the team repo, schema
    validation in CI (`sic validate --strict`), CODEOWNERS for sensitive
    sections (e.g., `do_not` rules).

### Phase 6 — ChatGPT memory importer (depends on Phase 1)
17. `sic import-chatgpt <export.json> --as personal` — parses the ChatGPT
    memory export format, runs it through a Claude prompt to classify each
    bullet into our schema sections, writes a draft personal profile for
    user review (the workflow from the article's Part 1).

### Phase 7 — Verification & docs (depends on all)
18. Test suite: unit tests for merger (every tier), golden tests for
    renderer, integration test that runs `sic init → sync → render` against
    a fixture team repo.
19. README with quickstart, schema reference, conflict-resolution flowchart,
    and a one-page diagram of the layer model.

## Relevant files (to be created)
- `pyproject.toml` — project metadata, `sic` entrypoint, deps
- `src/sic/schema.py` — Pydantic models + JSON Schema export
- `src/sic/loader.py` — YAML load/save preserving order & comments
- `src/sic/merger.py` — three-tier resolution engine
- `src/sic/llm.py` — Anthropic SDK wrapper for Tier-3 merges, with cache
- `src/sic/renderer.py` — CLAUDE.md generator (Jinja2 templates under `templates/`)
- `src/sic/cli.py` — `typer` commands
- `examples/team.yaml`, `examples/*.personal.yaml` — fixtures
- `tests/test_merger.py`, `tests/test_renderer.py`, `tests/golden/`
- `.github/workflows/validate.yml` — schema validation CI for team-profile repos
- `README.md` — quickstart & schema reference

## Verification
1. `pytest -q` — all merger tier rules covered; golden-file renderer tests pass.
2. `sic validate examples/team.yaml` exits 0; intentionally broken fixture exits non-zero with field path.
3. `sic merge examples/team.yaml examples/alice.personal.yaml` produces expected resolved YAML (snapshot test).
4. `sic conflicts examples/team.yaml examples/bob.personal.yaml` lists the seeded conflict and shows the three resolution options.
5. End-to-end manual test: run `sic render --target project` in a scratch repo, open Claude Code, ask "what are my SQL formatting preferences?" — verify it answers from the merged profile.
6. Re-run `sic render` twice with no input change → `git diff` shows zero changes (idempotency).
7. `sic import-chatgpt fixtures/chatgpt_export.json --as personal --dry-run` produces a reviewable draft without writing.

## Decisions
- **Storage**: git repo of YAML files (user choice). YAML over JSON for human edits + comments.
- **Conflict tiers**: personal → team → LLM-mediated (user choice).
- **Integration**: generate `CLAUDE.md` (recommended over MCP for v1 — simpler, native, no server to run). MCP is a Phase-2 option.
- **Language**: Python — best Anthropic SDK support + matches the article's data-team audience.
- **Out of scope for v1**: web UI, MCP server, real-time multi-user sync, RAG/vector memory (those are what mempalace/roampal do — different problem).

## Further Considerations
1. **LLM-merge cost control** — Tier-3 merges call Claude. Recommendation: hash-cache results and require an explicit `--allow-llm` flag the first time per session. Option A: cache + flag (recommended). Option B: never auto-call; always queue for human. Option C: auto-call freely.
2. **Personal profile privacy** — should personal YAML ever land in the team repo? Recommendation: never; `.gitignore` `*.personal.yaml` by default, store personals under `~/.sic/`. Confirm before locking this in.
3. **Versioning the schema** — profiles will evolve. Recommendation: embed `schema_version` at top of every YAML; `sic migrate` command added in Phase 7 if needed.
